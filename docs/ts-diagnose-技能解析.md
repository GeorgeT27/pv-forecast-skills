# ts-diagnose 引擎解析：它画了什么图、这些图怎么变成结论

> [!abstract] 一句话
> `ts-diagnose` 是一套通用的"结果诊断"工具：给定预测结果和真值，它会**自动画出一整套标准分析图**（误差结构、时效退化、模型对比、输入特征关联……），再按一套固定的验证流程，把图里看到的现象一步步升级成"可以对外讲"的结论——现象不够硬的会诚实地标注"证据不足"，不会夸大。

---

## 1. 这是干什么用的

`ts-diagnose` 是**通用诊断引擎**：当分析目标不属于那 4 个专用场景时（比如"训练是否充分"、"模型 A 为什么比 B 好"、"结论稳不稳"、"只想把图画一遍看看"），用它来做。

它最大的特点是**遇到不确定就停下来问，不会替用户瞎猜**——比如数据格式、判断标准这些一旦猜错就会污染后面所有分析的地方，它一定会先确认清楚再动手。

---

## 2. 整体怎么跑起来（四步）

```mermaid
flowchart LR
    A["① 摸底<br/>手头有什么数据、现在做到哪一步了"] --> B["② 生成分析代码<br/>先在已知答案的测试数据上验证准不准"]
    B --> C["③ 画图看现象<br/>调用一整套预先写好、验证过的标准图"]
    C --> D["④ 归因下结论<br/>现象 → 假设 → 验证 → 结论"]
```

**① 摸底**：进入分析前，有一个小脚本（`orient.py`）自动扫一遍工作目录，判断"现在做到哪一步了、还缺什么材料或者哪个问题没问清楚"。举例：如果昨天已经把预测和真值对齐好了，今天再跑一次，它会直接说"对齐已完成，当前该做差距分解画图，还差一个问题没答：这次要重点比较哪两个模型"。不需要每次从头交代一遍进度。

同时它会盘点"手头有哪些材料"——一共分 11 类，最常见的是：**模型的预测结果、对应的真值、模型代码、训练日志、输入的气象/预报特征、特征的真值对照、训练期的真值、模型权重、可调用的预测接口、实验配置、已有的数据画像**。不是每次都要凑齐全部——缺什么，对应用不到的图或分析就自动跳过，不会因为缺一样材料就卡住整个分析。

**② 生成分析代码并验证**：需要的计算脚本会现场生成，但**不会直接拿去跑真实数据**——会先在一份"答案已知"的测试数据上跑一遍，确认脚本没写错（比如某个变量确实被算出了"最重要"，脚本才算过关），再去碰真实数据。这道验证保证了图和数字不会因为脚本本身有 bug 而失真。

**③ 画图看现象**（详见下一节，这是最核心的部分）。

**④ 归因下结论**：图上看到的现象，不能直接写成"结论"——比如"模型 B 长期预测衰减更快"只是现象，还需要经过几道检验（差异是不是噪声、有没有其他解释、多个独立证据是否一致）才能升级为"可信结论"。没过检验的会如实标注"仅为初步现象/证据不足"，绝不虚报确定性。

---

## 3. 六个可选的诊断场景

同一套摸底、画图、归因流程，套在不同的问题上：

| 场景 | 回答什么问题 |
|---|---|
| **model-comparison** 模型对比 | 模型 A 为什么比 B 好/差，差距集中在哪里、能不能归因到架构机制 |
| **fact-scan** 图谱体检 | 只想把标准分析图画一遍看现象，不需要下结论 |
| **training-sufficiency** 训练充分性 | 训练是不是练到位了、哪部分训练数据在拖后腿 |
| **robustness** 鲁棒性 | 一个结论去掉几个极端样本、换个时间段还成不成立 |
| **feature-importance** 变量重要性 | 哪个输入变量对误差影响最大，该往哪投入数据/取舍特征 |
| **deployment-drift** 部署后退化/漂移 | 上线的模型是不是真的变差了、从哪天开始变的（是慢慢滑坡还是突然掉的，两种时点都会报）、能不能把变差归因到具体诱因 |

其中 **model-comparison** 和 **fact-scan** 是画图最集中的两个场景——两者都会调用下面这套完整图谱库；**deployment-drift** 调用的是其中偏"随时间变化"的一个子集。

## 4. ★ 核心：都画了什么图、图怎么变成归因

### 4.1 一套统一的"标准分析图库"，按 6 类归组

不管手头数据长什么样子，只要整理成统一的四列格式（**预报时刻｜站点/序列｜模型｜误差**），下面这 25 张图就都能自动生成——图的代码是提前写好、反复验证过的，不是每次现场现写现画，保证同一张图每次的算法都一样、可信。

每张图的元信息里都强制标了一个**类别**（少一个都过不了 CI 检查），一共 6 类：

| 类别       | 回答的是哪种问题                                          | 图数  |
| -------- | ------------------------------------------------- | --- |
| **误差结构** | 误差本身长什么样——集中在哪、是偏移还是形变、分布对不对、有没有残余可预测结构、是不是整体错了时间 | 9   |
| **时效稳定** | 表现随时间/口径切换是否稳，什么时候开始变的，历次预测是收敛还是跳变                | 5   |
| **模型对比** | 多个模型之间谁好、好在哪、能不能互补，排名差异是真的还是噪声，比朴素基线强多少           | 5   |
| **输入侧**  | 输入特征的质量/趋势和输出误差是否耦合，多变量组合出的"输入状态"是否分辨误差           | 3   |
| **样本对照** | 挑出具体的"坏点/坏窗口"看它们的性质，好坏窗口之间差在哪，坏窗口是一种失败模式还是几种      | 3   |
| **模型归因** | 把误差还原到模型内部机制（白盒/黑盒）                               | 3   |

下面每类配一张用合成数据实跑出来的示例图（不是手绘示意图，是图库脚本的真实输出）。

#### 误差结构（9）

| 图 | 回答什么问题 | 办法 |
|---|---|---|
| **error-breakdown** 误差结构分解 | 误差主要来自哪个维度（时段/站点/模型） | 按"单元 × 月份 × horizon 带"三个维度分别聚合成 RMSE 矩阵，取最差格子和各维度的边际曲线 |
| **intraday-profile** 日内曲线 | 一天中哪个时段误差最大（比如日出日落) | 按目标时刻的小时分箱聚合 RMSE/偏差，画成一条"日内曲线"，同时看正负偏差是否对称 |
| **horizon-degradation** 时效退化 | 预测得越远越不准，衰退有多快，哪个模型撑得更久 | 按预报步聚合 RMSE 曲线，早段/晚段各取一段做最小二乘直线拟合比较斜率，标出模型间的交叉点 |
| **horizon-error-quantiles** 逐步误差分位扇形 | 每往前多预测一步，误差分布（不只是均值）怎么变宽/变歪，该配多宽的置信带 | 按预报步分组，取误差分布的经验分位数（如 p10/p50/p90），画成随步数展开的分位扇形带 |
| **true-vs-pred-scatter** 真值-预测散点 | 整体拟合形态，是否存在系统性高估/低估 | 真值-预测值做线性回归取斜率/截距/R²，再按真值分位分箱看每箱的预测均值与残差分位 |
| **pp-calibration** 分位数校准 | 预测值的整体分布和真值的整体分布对不对得上——是不是系统性把大值压小了、小值抬高了 | 分位数-分位数对照（QQ-plot 变体）：预测值与真值各自取一组分位数，一一配对回归取斜率，另看两端尾部分位的比值 |
| **theil-decomposition** 误差三分解 | 误差是纯水平偏移（bias）、幅度不匹配（variance），还是形状/错位（covariance）——三种问题的修法完全不同 | Theil's U 不等系数分解：把总误差平方和拆成偏差占比、幅度不匹配占比、形状错位占比三部分 |
| **error-acf** 误差自相关 | 把误差序列本身（而不是原始数据）拿去做自相关检验——误差里还有没有可预测的周期/结构，还是已经是白噪声、没法再免费改进了 | 把每个预报窗口的均值误差按时间排成序列，算自相关函数（ACF），配合 Ljung-Box 检验判断是否显著偏离白噪声 |
| **time-shift-diagnosis** 逐窗最优时移 | 预测曲线形状对不对，只是整体提前/滞后了几步——这是"对时错位"，跟"预测得不准"是两回事，前者通常只要修数据管道的时间对齐就能免费改进 | 对每个窗口在若干候选平移步数里做 argmin 搜索（找让 MSE 最小的整体时移量），统计最优平移量在全体窗口上的分布 |

这类图大多长成"一条或几条曲线随某个维度（时段/预报步）走"的样子。下图是 `horizon-degradation` 的示例：两个模型的 RMSE 随预报步（0~23 小时）变化，模型 A 起步很准但衰减快，模型 B 起点较差但衰减平缓，中段出现交叉——这类"谁撑得更久"的问题就是这一大类图共同的看法。

![horizon-degradation 示例](assets/ts-diagnose-demo/error-structure-horizon-degradation.png)

#### 时效稳定（5）

| 图 | 回答什么问题 | 办法 |
|---|---|---|
| **rolling-stability** 滚动稳定性 | 表现随时间推移是否稳定，还是逐渐变差、从哪天开始变的 | 逐日聚合行 RMSE 均值做滚动曲线，贪心二分分段找变点（幅度超阈值才算），并按星期几分组看有无周期结构 |
| **cross-dim-stability** 跨维稳定性 | 换个时间段、换个考核口径，"A 比 B 好"这个方向还成立吗（防止一堆图其实都是同一份数据派生的"伪独立"证据） | 把数据按时间对半切、再按两种考核口径（行 RMSE 均值 vs 点级 pool）各重算一次差距，检查两次结果方向是否一致 |
| **train-test-drift** 训练/测试漂移 | 测试期数据和训练期数据是不是已经"变了天" | 按日历月计算测试期与训练期标签分布的 PSI（群体稳定性指数）和 KS 检验，超阈值的月份直接告警 |
| **y-vs-feature-mapping** 特征-功率映射 | 特征取值和功率的关系是否变了（分布是否漂移） | 按窗口中位数切成前后两期，各自把特征分箱后取对应的 y 均值曲线，比较两条曲线是否整体平移 |
| **revision-stability** 翻新稳定性 | 同一个目标时刻会被多个发起窗口反复预测——随着越来越临近（lead 变短），预测是收敛到真值，还是来回跳变，还是干脆塌缩贴着均值不动 | 把同一目标时刻在各发起窗给出的历次预测按 lead 降序串成一条"翻新轨迹"，算相邻两次预测的对称变化率（SMAPC）和"最短 lead 误差/最长 lead 误差"的收敛比 |

这类图看的是"一条误差曲线沿着日历轴走"，重点是找变点、看趋势。下图是 `rolling-stability` 的示例：模型 B 在 2 月初出现一次明显的台阶式恶化（红色虚线标出的变点），而模型 A 全程平稳——这正是"从哪天开始变的"这个问题的直观呈现。

![rolling-stability 示例](assets/ts-diagnose-demo/temporal-stability-rolling-stability.png)

#### 模型对比（5）

| 图 | 回答什么问题 | 办法 |
|---|---|---|
| **model-error-correlation** 模型误差相关性 | 两个模型是不是"错在同一批样本上"（同质化程度） | 计算模型两两之间逐样本误差的相关系数矩阵，找出相关最高（最同质）和最低（最互补）的模型对 |
| **worst-slice-compare** 最差片段对比 | 差距是集中在个别时间段，还是普遍存在（内置随机置换基线，防止把"随机也会挑出一个最差月"误判成真实规律） | 按月切片算每片的行 RMSE 均值差距，对差距最大的片做按日块整块随机置换（200 次）得到显著性 p 值 |
| **oracle-gap** 理论上限差距 | 距离"理论最优"还有多少提升空间，值不值得再投入 | 逐样本挑选误差最小的模型构造事后最优的"oracle"，比较 oracle 均值与实际最优单模型/ensemble 的差距 |
| **baseline-skill** 朴素基线技能阶梯 | 模型比"直接抄上一时刻"或"抄同周期相位"这种零智能的笨办法强多少？有没有模型其实已经退化成照抄输入了 | 构造几个零智能参照基线（persistence=抄发起时刻真值、seasonal-naive=抄上个周期同相位、climatology=抄全局均值；周期步长可指定或用自相关自动检测），算 skill=1−RMSE_模型/RMSE_基线，并检查模型预测是否离 persistence 基线比离真值还近 |
| **model-rank-significance** 排名显著性 | 几个模型排出来的名次差异是真的，还是样本量不够时的噪声？哪些模型统计上其实分不出高下 | 按行 RMSE 给每个样本内的模型排秩取平均秩，用 Nemenyi 临界差判断哪些模型的秩差"不可信"，再逐对做 Diebold-Mariano 检验（用 Newey-West 方差处理误差的自相关）给出配对显著性 |

这类图把两个（或多个）模型摆在一起比，常见形态是"对比柱状图 + 片段内逐日曲线"。下图是 `worst-slice-compare` 的示例：左边柱状图显示模型 B 在其最差月份（2 月）RMSE 明显高于模型 A，右边把这个月逐日展开，B 全月持续偏高，不是某一天的偶然——这就是"差距是集中爆发还是全月都差"这个问题的看法。

![worst-slice-compare 示例](assets/ts-diagnose-demo/model-comparison-worst-slice-compare.png)

#### 输入侧（3）

| 图 | 回答什么问题 | 办法 |
|---|---|---|
| **feature-error-conditional** 特征-误差条件关系 | 某个气象/预报特征异常时，功率误差是否也跟着变差 | 把特征取值或特征预报质量按分位数分箱（qcut），算每箱的 y RMSE，看箱序和 RMSE 是否单调（Spearman rho）、最差箱/最好箱的比值有多大 |
| **feature-trend-overlay** 特征趋势叠加 | 特征本身的预测走势和功率误差走势是否同步 | 自动挑出焦点模型表现最差的月份，把该月逐日的特征质量曲线和逐日的 y 误差曲线对齐，算两条曲线的相关系数 |
| **feature-regime-error** 多变量制式条件误差 | 单看一个特征分箱看不出来的——由好几个特征"共同组成"的输入状态里，哪一种状态下误差最重、占多大比例 | 把窗口级的多个特征值拼成向量、逐特征标准化后做无监督聚类（k 在 2~4 之间用轮廓系数挑），得到几种"输入制式"，比较各制式下的模型 RMSE |

这类图把"输入特征的质量/取值"放在横轴，"功率误差"放在纵轴，看两者是否耦合。下图是 `feature-error-conditional` 的示例：把辐照预报按预报质量分箱后，两个模型的 RMSE 都随箱序发生明显变化——说明这个输入特征的预报质量确实和功率误差挂钩，值得去交叉验证是不是它拖累了指标。

![feature-error-conditional 示例](assets/ts-diagnose-demo/input-side-feature-error-conditional.png)

#### 样本对照（3）

| 图 | 回答什么问题 | 办法 |
|---|---|---|
| **worst-points** 最差点定位 | 最差的那些点具体是什么时候、什么条件下出现的——是极值、转折点还是高波动时段 | 取误差绝对值最大的 top-N 点，用局部标准差、前后差分、自身分位数三个描述符给每个点打"极值/转折点/高波动/普通"标签（可叠加） |
| **good-bad-contrast** 好坏窗口对照 | 把预测最好和最差的一批窗口各挑出来，逐个输入特征、逐个通用背景变量（数值水平、波动率、时段）做对照——哪个特征在坏窗口里系统性地更差，是判断"输入拖累"还是"目标本身难预测"的直接证据 | 按行 RMSE 排序取最好/最差各 K 个窗口，逐特征算 Cohen's d 效应量和 KS 检验，按 \|d\| 排序看哪个特征在两组间显著分离 |
| **bad-window-clustering** 坏窗形态聚类 | 表现最差的那批窗口，其真值曲线是一种失败模式，还是好几种并存的失败模式？各占多大比例 | 取行 RMSE 最大的 top-N 个窗口，把每窗真值曲线做 z-score 归一化并重采样到统一长度，做无监督聚类（k 在 2~4 之间用轮廓系数挑），看能分出几种典型曲线形态、各自占比与均误差 |

这类图是"把误差最大的几十个点摘出来，按性质打标签、散在时间轴上看"，或者"把最好和最差两组窗口摆在一起对照"。下图是 `worst-points` 的示例：模型 A 最差的一批点里有一个孤立的极端离群点（红色，误差远超其余点），其余大多是同一量级的普通极值——一眼就能看出这批坏点里有没有"一个孤立异常"和"一片系统性偏差"的区别。

![worst-points 示例](assets/ts-diagnose-demo/sample-contrast-worst-points.png)

#### 模型归因


| 图 | 回答什么问题 | 办法 |
|---|---|---|
| **global-attribution** 全局特征贡献 | 哪些输入特征对模型输出贡献最大？哪些只影响短期预测、哪些专门拖累远端 horizon？ | KernelSHAP：把"玩家"设成特征，mask=0 时该特征换成背景序列（对历史窗口做 kmeans 聚类挑代表窗、取质心均值），mask=1 时换回真实序列，逐窗算出每个特征对输出的贡献，按 horizon 分桶后汇总成排名条图 + 特征×horizon 贡献热力图 |
| **lookback 依赖衰减** | 模型往回看多少步历史输入才真的有用——是只认最近几步（Transformer 系模型常见），还是依赖很长的历史？ | 按整块（不是逐点，省一个量级算力）遮蔽历史窗口，遮蔽区间按"主周期"分桶（第一步/前四分位/到主周期/超主周期），测遮蔽后 ΔRMSE 画出衰减曲线；能拿到梯度的白盒模型可以升级到"每个历史时间步×特征"的归因热力图，只能黑箱调用时退到整窗分辨率 |
| **worst-K 局部 waterfall** | 表现最差的这几个具体样本，误差具体是被哪个输入特征、往哪个方向、贡献了多少造成的？ | 对误差最大的 top-K（默认 20）行逐行做局部 SHAP 分解，用 shap 自带的 waterfall 图把每一行的输出拆到各输入特征头上，取最差的几行拼成网格图 |

三张图共用同一个新材料——`serving_api`（一个能被实时调用的预测接口）：预写脚本不碰用户的模型代码，只认运行时一个薄适配器（`predict_adapter.py`，契约是声明能力 `CAPABILITIES` + 一个 `predict(requests)` 函数），用户接 FastAPI 就在适配器里打 API、接本地模型就本地推理；`lookback-decay` 额外要求适配器声明 `perturb_lookback=True`，不满足时选择门照旧如实标注"不可画"而不是硬凑。


### 4.1.1 画图前有一道"选择门"

声明要画的图不是照单全收：进入画图阶段前会停一次，把"材料够、能画"和"材料不够、自动跳过"的图分组列出来，让用户一次确认——默认全选（不吭声就是画全套，保证不漏查），也可以主动删掉不需要的图（删了会在报告里注明"这块没查、留了缺口"），或者从图库里跨场景挑一张这次流程没预设声明、但材料已经够用的图加进来。要求至少两个模型才有意义的对比类图（比如模型误差相关性、跨维稳定性、理论上限差距、最差片段对比、排名显著性检验）会标出"需要≥2 个模型"，避免只有一个模型时被误加进去导致图直接报错。

### 4.2 图怎么一步步变成结论——以"模型 A 为什么比 B 好"为例

> [!example] 完整链条示例
> 1. **先看总差距**：算出 A、B 整体谁更准、差多少、这个差距是不是噪声（配对统计检验）。
> 2. **画图分解差距**：调 `horizon-degradation` 发现——B 在预测 30 步以后误差涨得明显更快，A 更稳；调 `worst-slice-compare` 发现这个差距在各个月份里普遍存在，不是只集中在某一个月。**这一步只是"现象"**：观察 + 数字 + 来自哪张图，不允许说"因为……所以……"。
> 3. **提出候选解释**：如果有模型代码，可以对照架构档案——比如 B 的长程建模能力比 A 弱，这能解释"预测越远衰减越快"的现象。这时候现象升级为"假设"，但还不能写进最终结论。
> 4. **交叉验证**：用另一张独立的图（比如总差距的排名方向）核对，是否和"假设"预言的方向一致。两条独立证据都指向同一个方向，"假设"才能升级。
> 5. **写结论**：只有走完上述验证的结论才会出现在最终报告里；验证不完整的，报告会写清楚"这是初步观察，尚未证实"。

**这套流程的核心价值**：保证呈现给管理层的每一条结论，背后都有图和数字支撑，且经过了"是不是巧合/是不是别的原因"的排查——不会出现"看图脑补出一个机制故事"的情况。

## 5. 可信度是怎么保障的

- **图和计算脚本先在"答案已知"的测试数据上验证过，才允许拿去分析真实数据**——防止脚本本身算错却没人发现；
- 每次结论都会附上"这次用的是哪版代码、哪份数据"的记录，方便复核——如果两次分析结果不一样，能立刻判断是数据变了还是代码变了；
- **防"随机也能凑出一个规律"**：像"最差片段对比"这类容易被巧合带偏的图，内置了随机置换基线，点名之前先问一句"这比随机乱排还差吗"；
- **防"多图同源当成多条证据"**：所有图基本都是同一份预测数据算出来的，方向一致不代表互相独立佐证——`cross-dim-stability` 专门换时间段/换口径重算一遍，给出一条真正独立的稳定性证据；
- **图和标签不许带专业术语**：图的 id、字段名、图上标签、判读文字里不允许出现"天气""站点""光伏"这类具体领域名词（有清单硬卡），领域相关的说法只能在运行时经用户提供的背景信息临时加到呈现层——这样同一套图库不用改代码就能套到光伏以外的时序问题上；
- 中文字体渲染做了硬化：以前偶尔会因为环境缺字体，图上的中文标签变成方块，现在改成多级备选字体自动回退，并会报告实际用上了哪款字体；
- 一次用弱模型做的压力测试暴露过一个坑：把"什么时候趋势线发生转折"（changepoint）和"什么时候实际开始变差"（onset）当成一回事，会把"其实一周前就已经开始滑坡"误判成"上周才发生"——现在两个时点分开算、一起报，不再混用；
- 一个分析场景反复验证有效之后，可以"固化"成一个专门的轻量工具，以后遇到同类问题不用再从头问一遍。
