# 阶段 1 补充：上游修改清单（定稿后才动文件）

阶段 1 主文档只覆盖了新 playbook 本体的设计；本清单把隐含的上游修改逐条落成任务。执行顺序：先过本清单的三个待拍板决定 → 按"必改"清单动文件 → 新 playbook 本体 → 验收。

## A. 必改（不改则新 playbook 跑不起来）

### A1. model-audit playbook
- 新增产出一：**完备差异清单**（模型对比场景）。硬规则：逐行对比两模型代码，覆盖 forward 之外的 `__init__`/初始化/默认参数；清单不完备 = 假设空间有洞 = 错误归因（C3 教训：初始化差异藏在 `__init__`，漏掉就会把 0.009 错归给分解）。
- 新增产出二：**组件→可干预开关映射**。每个组件标注：现成配置项（如 `--n_heads`）/ 需加代码开关（如 `--itrans_no_attn` 类置零 stub）/ 不可干预（标明原因）。阶段 1 主文档 §2 上游表已假设此产出存在，但现有 model-audit 没有——本条就是补这个洞。
- done：model_profile 产物 schema 增加 `diff_list`（含完备性自检声明）与 `ablation_switches` 两个字段。

### A2. model-comparison playbook
- §3 升级规则"假设→已证实"增加一条路径：architecture-attribution 产出的消融 receipt（与现有"用户提供外部实验"并列，成为可执行版本）。
- §4 停顿点汇报增加第⑥件事：存在机制假设且检测到可重训框架材料时，提示"可续接 architecture-attribution 做干预验证"。
- done：两处文字落位，不动其余任何章节。

### A3. conclusion_gate（引擎级，管全部 playbook 的结论）
- 新增 `ablation_receipts` 字段：每条 receipt 含配置 diff、实测 delta、噪声底对照、种子数、判定（确认/否证/未决）。
- 新增拦截规则：结论文本含架构/组件因果表述而无对应 receipt → 拦截，强制降级为"未验证假设"并显式标注。
- 现有闸行为对老结论完全向后兼容（无因果表述则不触发）。
- done：构造反例测试通过——一条无 receipt 的架构因果结论被实际拦截（阶段 1 主文档验收标准 2）。

### A4. _playbook-spec / 产物注册表
- 注册新产物类型：`noise_floor`（≥3 种子方差表 + 3σ 线）、`ablation_receipts`。
- done：spec 文档与 orient 的产物解析同步。

### A5. SKILL.md + orient 路由
- 注册 architecture-attribution：触发条件（机制归因诉求 + 可重训框架材料在场）；升级条件写明"model-comparison 停在假设层级且用户要机制结论时续接"。
- orient 材料清单增加一项材料类型：`trainable_framework`（训练入口脚本 + 可复现实验的配置）。缺此材料时新 playbook 不解锁，全线行为与现状一致（零破坏声明）。
- done：路由表 + 材料表各加一行。

### A6. ts-diagnose-v2 同步
- 新 playbook 薄卡一张 + 派发表加一行（保持 v1/v2 A/B 可比）。
- done：v2 目录卡片落位。

## B. 建议改（不阻塞新 playbook，可与 A 同轮或延后）

### B1. training-sufficiency playbook
- 理由：评测集实证训练配置类结论同样需要干预且反直觉——T1（lr×50 在 DLinear 上无效，调度自愈）、HT2（同注入在 PatchTST 上训炸且 z 公式误判）、T2（欠训练签名）。
- 改动：其训练配置因果结论走同一条 `ablation_receipts` 升级路径（重训干预=改一个训练超参重跑 ≥3 种子）。
- 不改的后果：该 playbook 结论停在假设层级，与现状相同，无回归。

## C. 不改（明确记录，防止误伤）

- feature-importance：feature-blame v3 已自带反事实预算阶梯，机制等价。
- subset-influence：Mode B checkpoint 变体就是干预。
- data-setup / fact-scan / metric-eval / result-eval / robustness / deployment-drift：纯事实生产或已有验证机制。
- 以上除 receipt 格式对齐（见决定 3）外一律不动。

## D. 三个待拍板决定（动文件前必须先定）

1. **噪声底产物由谁生产？**
   - 选项 a：data-setup 加变体（噪声底本质是"同配置多种子跑数据"，与 setup 的对齐职责同源）；
   - 选项 b：新增独立小 producer playbook；
   - 选项 c：作为 architecture-attribution 的内部 Stage 0（不注册为共享产物）。
   - **建议：a**——噪声底可被 model-comparison / training-sufficiency 复用，应是共享产物；独立 producer（b）对一个方差表来说太重。
2. **training-sufficiency（B1）本轮改还是延后？**
   - **建议：本轮一起改**——改动只有一处升级路径引用，且评测集里已有三道现成题（T1/T2/HT2）覆盖它，进化循环可以直接练到。
3. **receipt 格式是否统一到 feature-blame v3 现有反事实格式？**
   - **建议：统一**——conclusion_gate 只认一种 `ablation_receipts` schema，feature-blame 的反事实记录做一次字段映射，避免闸里长出两套证据格式。
