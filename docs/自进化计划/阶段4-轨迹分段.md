## 1. 问题诊断（C1 实测）

### 1.1 phase 字段存在，但实跑没分成段

C1 的 24 条事件里只有 6 条带 `phase`，其中 5 条是收尾同一秒（09:19:01）批量补记的：

```
08:50  runner  prepare / launch
08:51  orient  route → blocked
08:55  orient  phase_enter stage-0        ← 唯一一个 enter
       ………… 24 分钟真正干活的时间，0 条带 phase 的事件 …………
09:14  journal intervention_receipt ×4   phase=''  ← 四条同一秒
09:19  orient  phase_exit stage-0/1/2/3/4          ← 五个 exit 同一秒
09:19  orient  workflow_complete
09:20  runner  exit / skill_load_verify / collect
```

根因：`eval_trajectory.transitions()` 的事件来自 `diagnose_state.json` 的状态差分，只在 agent 主动跑 `orient.py` 时落盘。C1 跑了 5 次 orient、一次未带 `--goto`，最后一次运行时五个 stage 一起从 todo 翻成 done。**没有任何机制强制 agent 每完成一个阶段报到一次。**

现有两个钩子都覆盖不到中间：`orient_reminder.py` 是 `UserPromptSubmit`，headless 里整场只响一次（其 docstring 已自承"agent 内部多轮不触发"）；`gate_guard.py` 是 `Stop`，只在收工时响一次。

### 1.2 排序模式：纯时间戳排序，且时间戳有真有假

`trajectory.merge_logs()` 的排序键是 `(timestamp, SOURCE_PRIORITY, 原日志行号)`，`seq` 是排完后重编的号，不是记录。可靠性完全取决于时间戳：

| 来源 | 时间戳来源 | 可靠 | C1 条数 |
|---|---|---|---|
| runner | 事件发生当下 | ✅ | 5 |
| orient | 事件发生当下 | ✅ | 6（只报到 2 次） |
| journal | **产物文件 mtime**（`build_journal._ts()`） | ❌ | 9 |
| agent 自报 `DECISIONS.jsonl` | 事件发生当下 | ✅ | **0（C1 未产出）** |

H1–H4 四条 receipt 事件全读同一个 `receipts/receipts.json` 的 mtime，时间戳完全相同（09:14:58），最终顺序由"在日志里的行号"决定——**是编出来的**。真实情况是四个子代理在 09:09–09:12 并行跑完。

### 1.3 事后从 mtime 倒推行不通（实测反例）

按各 stage 的 `done_when` 产物 mtime 倒推阶段边界：

```
stage-1  09:06:09 → 09:15:34    9.4 min
stage-2  09:15:34 → 09:09:02   -6.5 min   ← 负数
```

`hypothesis_ledger.json` 在 Stage 1 产出，Stage 3 判完后被回填重写，mtime 变成最后一次写入。**mtime 只说明"最后一次动它是什么时候"，不说明"它是什么时候产出的"。** C1 实测有 4 个产物存在这种回写。

### 1.4 反思拿到的材料没有顺序

进入反思 bundle 的 23 个文件按 `index.json` 顺序内联，而 `collect.changed_files()` 用 `sorted()` 排序 → **文件名字母序**：`CONCLUSION.md` 排第一（最后写的），`slice_zcheck.json` 排倒数第二（Stage 0 的事实）。

唯一写清了先后顺序的 `PROGRESS.md`，`reflection_default=false`，**默认被排除在反思之外**。

### 1.5 分析脚本是孤儿

主线四个文件的交叉引用实测结果：

```
hypothesis_ledger.json  → 引用脚本 无
intervention_plan.json  → 引用脚本 无
receipts/H1.json        → 引用脚本 无（18 个字段无一指向 eval_H1.py）
verdict_summary.json    → 引用脚本 无
provenance.json         → 8 个脚本的 sha256，但不知哪个服务哪条假设
```

假设 ↔ 干预 ↔ 判决靠 `hypothesis_id` 互认，但 `eval_H1.py` 与 H1 之间唯一的联系是**文件名里那个 "H1"**——机器读不出来的命名约定。

后果：若 `eval_H1.py` 的切片逻辑写错，receipt 里的 delta 是错的，但 receipt 表面完全正常（per_seed、符号一致性、保守口径复核一应俱全）。反思会判定"这一步做对了"，真正的问题在孤儿脚本里，没有任何线索指向它。**错的不是判断，是判断依据的生产过程，而生产过程没有被链进任何可追溯的线。**

### 1.6 PROGRESS.md 的机器审计线被 agent 覆盖

`orient._write_state_progress()` 每次运行都往 `PROGRESS.md` 追加一行带时间戳的记录。C1 跑了 5 次 orient，文件里只剩 1 行——agent 把它当叙事文档整篇重写了（文件头是 `# PROGRESS —— tier2-c1 / architecture-attribution`，非 orient 模板头）。这是个"存在但不工作"的机制，留着制造有审计线的错觉。

## 2. 设计：两个正交维度 + 一类区间

### 2.1 三者的分工

| 概念 | 回答什么 | 是不是时间 |
|---|---|---|
| `timestamp` | 什么时候 | **唯一的时间事实** |
| `segment_id` | 在哪一段（阶段） | 否，是分组标签；因为段间串行，顺带提供粗粒度顺序 |
| `episode_id` | 属于哪条假设 | 否，纯归属标签，**本身不含顺序** |

`segment` 是时间轴上的切分，`episode` 是因果链上的切分。**两者正交，不能二选一**——H1 横跨三段：

```
H1 出生   第 5 段  hypothesis_ledger.json
H1 设计   第 6 段  intervention_plan.json
H1 执行   第 7 段  子代理 09:09:49–09:11:42
H1 判决   第 7 段  receipts/H1.json
```

episode 内部的顺序由各拍所在的 segment 排出，**不另编步骤号**。

### 2.2 段主键必须带命名空间

一条完整链（model-comparison → architecture-attribution）共 12 段，其中 `stage-0` 出现 3 次、`stage-1` 出现 3 次；且阶段闸允许 `--goto` 回退重跑同一 stage。因此主键 = **进入序号 + playbook + stage**：

```
01-intake
02-data-setup-stage-0
...
08-architecture-attribution-stage-1
13-architecture-attribution-stage-1     ← 回退重跑，序号不同，天然区分
```

### 2.3 并行的部分记区间，不记顺序

第 7 段里 H1–H4 是四个子代理并行跑的，**它们本来就没有先后**。正确记法是四个可重叠的 `(t_start, t_end)`，不是四个点。C1 实测区间：

```
H1 09:09:49–09:11:42  113s
H2 09:10:09–09:11:56  108s
H3 09:10:37–09:12:43  126s
H4 09:10:55–09:12:39  105s     ← H1 与 H4 重叠 47 秒
```

子代理不需要新的编号体系，它是 **segment × episode 的交点**：`{agent_id, segment_id, episode_id, t_start, t_end, transcript}`。

子代理**内部**的步骤不再编号——那份 JSONL 本身有序，上层只留指针。

**已知缺口（未实施）**：Stage 3 判完后追加 post-hoc 假设并当轮再干预时，playbook 不要求退回 Stage 2，orient 状态机没有跳转 → 不会分裂新段，追加轮全部落在同一个 stage-3 段里。episode 各自的时间戳仍能排出先后（H5 的出生晚于 H1–H4 的判决），且"设计动作发生在 stage-3 段内、没有对应 stage-2 段"这件事本身就是可供反思的信号。若要段一级可见，须改 playbook 强制退回 Stage 2 走新的 pause_after——SOP 改动，另行决策。

### 2.4 12 段的完整清单（model-comparison + architecture-attribution）

```
 #   段                        归属                        出口标志
 1   材料盘点（入口闸）          引擎                       五件套齐 → 解除 BLOCKED
 2   适配与对齐                data-setup   stage-0       predictions.csv + alignment_report
 3   产物清单落盘              data-setup   stage-1       setup_manifest.json
 4   总差距事实                model-comparison stage-0   gap_summary.json      ★分流点
 5   差距分解（事实）           model-comparison stage-1   charts/*.json+INDEX   ★停顿
 6   机制归因（产假设账本）      model-comparison stage-2   hypothesis_ledger     ★停顿
```

## 3. 抽取器 vs 埋点：两件事，不是二选一

| | 抽取器 `runner/segments.py` | 探针 `hooks/stage_probe.py` |
|---|---|---|
| 用途 | **只给已跑完的 run 回填** | 新 run 的生产机制 |
| 数据来源 | 转录反推 | 发生当下直接记 |
| 寿命 | 探针上线后只服务历史 run | 长期 |

倒推不作生产机制的理由：它是**不会报错的猜**，段边界错了不会有异常，反思照样信。九成对的重建比没有更危险。

不做抽取器的代价：C1/C2/C3 + Tier1 八案例已跑掉的 run 全部无段结构，只能作废重跑。

**衔接**：`journal` 类事件本来就是收卷后从产物抽取的，没有"运行时"可言。这类事件的段归属靠**按时间戳查段表**——只要段表由探针实录，查表是准的，不是猜。

### 3.1 样例验证结论（2026-08-20，只读重建 C1）

重建脚本读 `transcript.raw.jsonl` + `subagents/agent-*.jsonl`，产出九段：

```
段                          进        出       时长    备注
01-intake                08:50:43  08:55:26   4m43s
02-data-setup            08:57:33  09:02:09   4m35s   ↻回写 setup_manifest@09:01:47
03-model-profile         09:01:20  09:01:35   0m15s   ← 与上段重叠，主 agent 边等边干
04-arch-attr-stage-0     09:04:03  09:04:47   0m43s   ↻回写 noise_floor@09:06:09
05-arch-attr-stage-1     09:06:43  09:08:06   1m23s   ↻回写 ledger@09:15:35（跨 3 段）
06-arch-attr-stage-2     09:08:06  09:09:02   0m56s   ↻回写 plan@09:11:05
07-arch-attr-stage-3     09:09:02  09:14:58   5m56s   4 子代理并行，区间见 §2.3
08-arch-attr-stage-4     09:14:58  09:18:52   3m54s   ⚠ conclusion_gate.json 无产出时刻
09-finish                09:18:52  09:20:34   1m42s
```

**关键发现：不埋点就能拿到 9/9 段边界。** 主 transcript 每行带毫秒时间戳，每次 Write/Edit/Bash 都能定位到秒。原判断"必须先埋点才有时间"不成立。

可填性统计：

| 字段 | 可填 | 说明 |
|---|---|---|
| 段边界 t_enter/t_exit | **9/9** | 全部来自转录，非 mtime |
| 子代理区间 | **5/5** | 含 4 个并行重叠 |
| 出口产物产出时刻 | **8/9** | 缺 `conclusion_gate.json`——引擎脚本内部写的，命令行看不见路径 |
| `paused`（该停有没有停） | **0/2** | 完全无记录 |
| `gate`（闸归属） | **0/9** | 无归属字段 |
| 产物按段归集 | **0/45** | 需按段窗口归集，不能用 mtime |

因此探针的定位从"地基"降为"补最后三个洞"：`paused`、`gate`、脚本内部写出的产物。

样例产物与构建脚本：`segments.sample.json` / `build_segments_demo.py`（2026-08-20 会话 scratchpad，未入库；正式实现时重写为 `runner/segments.py`）。

## 5. 依赖关系

```
第 0 步 ──── 独立，随时做
第 1 步 ──┬─ 第 2 步要用（抽取器得往事件上打 segment_id）
          └─ 第 5 步删 phase/seq 的前置
第 2 步 ──── 救历史 run，可与第 3 步并行
第 3 步 ──┬─ 第 5 步删 mtime 的前置
          └─ 第 6 步 episode 完整链的前置
第 4 步 ──── 补最后三个洞
第 6 步 ──── 依赖 1+2+3
```

## 6. 验收标准

| 项 | 标准 |
|---|---|
| 段边界 | 新 run 的 `segments.json` 每段有 `t_enter`/`t_exit`，`fill=real`；与探针实录一致 |
| 回写可见 | `done_when` 产物同时记 `produced_at` 与 `rewritten_at`，C1 那 4 个回写全部显式 |
| 并行如实 | 同段内并行子代理记为可重叠区间，不排成序列 |
| episode 闭合 | H1 的四拍（出生/设计/执行/判决）各有 `segment_id` + 时间，脚本经 `script_sha256` 与回执对得上 |
| `paused` | 两个 `pause_after: true` 段能判定停没停 |
| 无假时间 | 全库 grep 无 `mtime` 作为事件时间戳的用法 |
| 反思材料 | bundle 按段组织，`PROGRESS.md` 在内，setup 搬运脚本不在 |

## 7. 与阶段 3 的接口

本阶段完成后，阶段 3 §2.4「反思归因」的输入从"23 个字母序排开的散件 + 时序半假的事件流"变成"按段组织的时间线 + 闭合的 episode 链"。这使 credit assignment 从 **run 级**（这一轮跑得好不好）下沉到 **step 级**（哪一段、哪条假设、哪个脚本出的问题）——阶段 3 §2.5 的"条目级增量编辑"才有明确的编辑对象。

C1 的具体例子：现在只能说"归因结论偏弱"；改造后能说"第 5 段登记账本用了 1m23s、第 7 段 H1 的 eval 脚本改了 3 版"，前者指向"假设起草太仓促"，后者指向"写完代码要再三验证"——**两条完全不同的 skill 编辑**。
