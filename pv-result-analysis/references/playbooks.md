两类高频问题走固定流程：每步有判据、有分支，任何一次会话进来都走同一条路，结论质量不依赖当次发挥。
下结论都要过“结论三道门”（稳健性门槛 + 假设登记 + 反驳门，见 `analysis-discipline.md`）。

## Playbook A：“为什么 X 月变差了？”

1. **先查台账与事件**：读 `FINDINGS.md`（是否已分析过）和 `references/event-log.md`（X 月前后有无
   模型改版/气象源切换/限电/扩容）。有事件 → 先按事件日拆段重算指标，排除事件影响再谈模型能力。
2. **图#3 定位口径**：只有短期口径掉而超短期没掉 → 指向远时效/NWP 质量；全口径同掉 → 指向天气或数据。
   ods 与非 ods 差距拉大 → 误差集中在少数坏天。
3. **图#4 + #7 定位坏天**：坏天连续成片 → 天气过程；均匀散布 → 系统性退化。
4. **图#8 占比分解**：X 月 vs 基准月，五类天气占比变化 × 各类内 RMSE 变化——回答“是天变坏了，还是
   模型变弱了”。这是 Playbook A 的核心分解。
5. **图#11/#12 分布漂移检查**：X 月的天气/功率/映射分布 vs 训练年（2024）同月——偏出训练分布 →
   “模型没见过这种天”成为候选解释（见 `drift-and-nwp.md`，用 `run_drift.py`）。
6. **（NWP 模块验证可用后）图#10**：SSRD/GHI 预报误差月度曲线是否同步上升——区分“原料坏了”与
   “模型退化”（见 `drift-and-nwp.md`）。
7. **对照先验、过反驳门写结论**：三大候选解释（天气占比变化/分布外/NWP 原料变差）逐一给出支持或排除
   的证据，结合 `seasonality.md` 该站该月的先验机制形成结论。落 FINDINGS.md 前**走一遍反驳门七条**
   （见 `analysis-discipline.md`），并引用/更新 `references/hypotheses.md` 相关条目 ID；缺背景信息就明说
   并提请用户补 references/，不编造。

## Playbook B：“为什么模型 A 比 B 好（差）？”

1. **图#2 同质化检查**：over_error 相关 >0.95 → 差距大概率来自个别时段，直接跳第 3 步找具体时段。
2. **图#8 分天气类型对比**：差距来自哪类天（晴天都一样、多云天拉开 → 能力差异在气象不确定性处理上）。
3. **图#4 + #6 定位时间**：差距集中的日期与日内时段（爬坡段/正午/低估时段的不对称性）。**读到某形态
   想不出机制时查 `references/figure-diagnostics.md`**——它按“形态→候选机制”反向索引，把该现象翻成
   一组待验证假设（含挂靠的 H-ID），扩大候选集防漏诊。
4. **图#5 分时效对比**：近时效差距大 → 历史功率惯性利用的差异；远时效差距大 → 气象特征利用的差异。
5. **对照 models.md + hypotheses.md 验证机制**：用特征/架构差异解释上述现象（如 B 没用 SSRD 多点位
   特征 → 多云天更差），并引用 `references/hypotheses.md` 对应假设 ID（命中则据本次证据更新其状态；
   无对应条目先新增“预注册”再验）。`figure-diagnostics.md` 给的是候选假设、非结论，认领 ID 后仍须过
   稳健性门槛 + 反驳门。models.md 空字段 → 结论标注“机制待补模型档案后确认”。
6. **过稳健性门槛 + 反驳门**（Wilcoxon + 剔坏天 + 反驳门七条，见 `analysis-discipline.md`）后落
   FINDINGS.md，结论带上假设 ID。

## 面向主管的结论汇报（CONCLUSION.md，Stage 4 收尾）

三份文档构成金字塔，读者不同、写法必须不同——不要把它们写成一个样子：

- `figures/**/ANALYSIS.md`：逐图详证，读者是分析者/后续模型，证据密集。
- `FINDINGS.md`：结论台账，读者是分析者/模型，带状态、假设 ID、反驳门记录，为严谨而生。
- **`CONCLUSION.md`（工作目录根下，Stage 4 完成后写）：读者是主管**，为“快速读懂 + 能拍板”而生。

主管的痛点是**前两份太严谨、表格太多、读起来不直接**。CONCLUSION.md 是把已成立的结论**翻译**成
管理层语言，不是再堆一遍证据。它**不产生新结论**——只综合 FINDINGS.md 里状态为“已证实”（及少量
必要的“假设”，须显式标“初步”）的条目，可信度不够的不往上写。

写作纪律（针对“表格太多不直接”这条反馈）：

- **叙述优先，砍表格**：默认用短段落把逻辑讲清；**全文表格最多一张**（如模型排名或月度趋势总览），
  其余数字写进句子里。宁可多写两句话，不要让主管去表格里自己找结论。
- **金字塔、先结论后论据**：开篇一句话给最重要的结论（带 1 个最关键的数字）；然后 3–5 条关键发现，
  每条 = 结论 + **一个**支撑数字 + 一句大白话的原因（挂靠电站/模型事实但去术语化，如“这个模型倾向于
  把大晴天的午间发电压低估”而不是“L1 损失导致条件中位数回归压峰”）。
- **方法论机器不进正文**：反驳门、假设 ID、Wilcoxon、PSI 这些不出现在正文；它们保证了结论可信，但
  主管不需要读。可信度用大白话在末尾一小段带过（哪些是站得住的定论、哪些是初步）。
- **给行动**：结尾写“建议/下一步”——分析的价值最终要落到主管能做的决定上。
- **诚实**：不确定的就说初步、样本少就说样本少，不把未过反驳门的结论粉饰成定论。

推荐结构（`CONCLUSION.md`）：

```markdown
# 结论汇报：<电站> <分析范围>（面向管理层）
_数据基础：<测试集范围/样本天数>；详见 FINDINGS.md 与 figures/ 下分析_

## 一句话结论
<最重要的一条，含最关键的 1 个数字>

## 关键发现
- <结论一>。<1 个支撑数字>。<一句大白话的原因>。
- <结论二>。…（共 3–5 条）

## 业务影响与建议
- <可执行的下一步/决策建议>

## 可信度说明
<两三句：哪些已站得住、哪些还是初步判断、有无需要留意的数据/事件保留>
```

写完照“展示纪律”（见 `analysis-discipline.md`）把 CONCLUSION.md 直接呈现给用户，不只报路径。
