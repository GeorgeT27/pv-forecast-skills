两类高频问题各走一条固定流程：每一步都有判据、有分支。好处是任何一次会话进来都走同一条路，结论质量不依赖当次临场发挥。两类问题下结论都要过“结论三道门”（稳健性门槛 + 假设登记 + 反驳门，见 `analysis-discipline.md`）。

## Playbook A：“为什么 X 月变差了？”

1. **先查台账与事件**：读 `FINDINGS.md`（看是否已分析过）和 `<project-context>/event-log.md`（看 X 月前后有没有模型改版/气象源切换/限电/扩容）。有事件 → 先按事件日把数据拆段、重算指标，排除事件影响之后再谈模型能力。
2. **图#3 定位口径**：只有短期口径掉、而超短期没掉 → 指向远时效/NWP 质量；全部口径一起掉 → 指向天气或数据。ods 口径与非 ods 口径的差距拉大 → 误差集中在少数坏天上。
3. **图#4 + #7 定位坏天**：坏天连续成片 → 是一次天气过程；坏天均匀散布 → 系统性退化。
4. **图#8 占比分解**：拿 X 月和基准月比，看五类天气的占比变化 × 各类天内的 RMSE 变化——回答“是天变坏了，还是模型变弱了”。这是 Playbook A 的核心分解。
5. **图#11/#12 跨站漂移检查**：拿留出站 X 月的天气/功率/映射分布，与训练站集合（pooled + 逐站）比。若偏出训练站分布 → “模型没见过这个站的这种天（跨站 OOD）”成为一个候选解释，同时看它最像哪个训练站（见 `drift-and-nwp.md`，用 `run_drift.py`）。
6. **（NWP 模块前提验证通过后）图#10**：看 SSRD/GHI 的预报误差月度曲线是否与功率误差同步上升——用来区分“原料坏了”还是“模型退化”（见 `drift-and-nwp.md`）。
7. **对照先验、过反驳门后写结论**：对三大候选解释（天气占比变化 / 分布外 / NWP 原料变差）逐一给出支持或排除的证据，再结合 `<project-context>/seasonality.md` 里该站该月的先验机制，形成结论。落 FINDINGS.md 前**走一遍反驳门七条**（见 `analysis-discipline.md`），并引用/更新 `references/hypotheses.md` 的相关条目 ID；缺背景信息就直说，并请用户补 references/，不要编造。

## Playbook B：“为什么模型 A 比 B 好（差）？”

1. **图#2 同质化检查**：若 over_error 相关 >0.95 → 差距大概率来自个别时段，直接跳到第 3 步去找具体时段。
2. **图#8 分天气类型对比**：看差距来自哪类天（晴天大家都一样、多云天才拉开 → 能力差异在于处理气象不确定性）。
3. **图#4 + #6 定位时间**：找出差距集中的日期与日内时段（爬坡段/正午/低估时段的不对称性）。**读到某个形态却想不出机制时，查 `references/figure-diagnostics.md`**——它按“形态→候选机制”做反向索引，把该现象翻成一组待验证假设（含挂靠的 H-ID），扩大候选集、防止漏诊。
4. **图#5 分时效对比**：近时效差距大 → 差在对历史功率惯性的利用；远时效差距大 → 差在对气象特征的利用。
5. **对照 models.md + hypotheses.md 验证机制**：用特征/架构差异去解释上述现象（例如 B 没用 SSRD 多点位特征 → 多云天更差），并引用 `references/hypotheses.md` 的对应假设 ID（命中则据本次证据更新其状态；无对应条目先新增“预注册”再验）。`figure-diagnostics.md` 给的是候选假设、不是结论，认领 ID 后仍须过稳健性门槛 + 反驳门。models.md 里字段为空 → 结论标注“机制待补模型档案后确认”。
6. **过稳健性门槛 + 反驳门**（Wilcoxon + 剔坏天 + 反驳门七条，见 `analysis-discipline.md`）后落 FINDINGS.md，结论带上假设 ID。

## 面向主管的结论汇报（CONCLUSION.md，Stage 4 收尾）

这套流程会产出三份文档，它们构成一个金字塔。读者不同，写法就必须不同——不要写成一个样子：

- `figures/**/ANALYSIS.md`：逐图详证，读者是分析者或后续的模型，证据密集。
- `FINDINGS.md`：结论台账，读者是分析者/模型，带状态、假设 ID、反驳门记录，为严谨而生。
- **`CONCLUSION.md`（工作目录根下，Stage 4 完成后写）：读者是主管**，为“快速读懂 + 能拍板”而生。

主管的痛点是：**前两份太严谨、表格太多、读起来不直接**。CONCLUSION.md 的任务是把已成立的结论**翻译**成管理层语言，不是把证据再堆一遍。它**不产生新结论**——只综合 FINDINGS.md 里状态为“已证实”的条目（以及少量必要的“假设”，且必须显式标“初步”）；可信度不够的不往上写。

写作纪律（针对“表格太多不直接”这条反馈）：

- **叙述优先，砍表格**：默认用短段落把逻辑讲清；**全文表格最多一张**（比如模型排名或月度趋势总览），其余数字写进句子里。宁可多写两句话，也不要让主管自己去表格里找结论。
- **金字塔、先结论后论据**：开篇一句话给出最重要的结论（带 1 个最关键的数字）；然后 3–5 条关键发现，每条 = 结论 + **一个**支撑数字 + 一句大白话的原因。原因要挂靠电站/模型事实但去掉术语，例如写“这个模型倾向于把大晴天的午间发电压低估”，而不是“L1 损失导致条件中位数回归压峰”。
- **方法论机器不进正文**：反驳门、假设 ID、Wilcoxon、PSI 这些都不出现在正文里；它们保证了结论可信，但主管不需要读。可信度用大白话在末尾一小段带过（哪些是站得住的定论、哪些还是初步）。
- **给行动**：结尾写“建议/下一步”——分析的价值最终要落到主管能做的决定上。
- **诚实**：不确定的就说初步、样本少就说样本少，不把没过反驳门的结论粉饰成定论。

推荐结构（`CONCLUSION.md`）：

```markdown
# 结论汇报：<电站> <分析范围>（面向管理层）
_数据基础：<测试集范围/样本天数>；详见 FINDINGS.md 与 figures/ 下分析_

## 一句话结论
<最重要的一条，含最关键的 1 个数字>

## 关键发现
- <结论一>。<1 个支撑数字>。<一句大白话的原因>。
- <结论二>。…（共 3–5 条）

## 业务影响与建议
- <可执行的下一步/决策建议>

## 可信度说明
<两三句：哪些已站得住、哪些还是初步判断、有无需要留意的数据/事件保留>
```

写完后，照“展示纪律”（见 `analysis-discipline.md`）把 CONCLUSION.md 的内容直接呈现给用户，不要只报路径。
