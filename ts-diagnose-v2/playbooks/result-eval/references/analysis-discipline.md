# 结论纪律细则（稳健性门槛 · 假设登记 · 反驳门 · 样本量 · 台账 · 运行后回顾）

     下结论（尤其标“已证实”）前来这里逐条对照。强制力由 SKILL 正文的精简版 + 常见错误 ❌ 清单守住。-->

一条结论要经得起三道门，缺一不可：

1. **稳健性门槛**——差异是不是噪声；
2. **假设登记**——先写预测、后看图；
3. **反驳门**——差异是不是别的原因造成的。

三道门都过，才可以在 FINDINGS.md 里标“已证实”。

## 1. 模型对比结论的稳健性门槛

写“A 比 B 好”之前，必须过两道检查：

1. 对按天配对的差值做 **Wilcoxon 符号秩检验**（或 bootstrap），且结果显著；
2. **剔除最差 3 天**之后，结论方向不变。

任一不过 → 把结论改写成“差异不显著”或“差异由个别极端天驱动”。0.5% 的指标差可能只是噪声；一个没过门槛的比较结论，比没有结论更有害。代码：`data_utils.robustness_check(rmse_a, rmse_b)`，返回 `passed=True` 才可下结论。

## 2. 假设登记（先预测后看图）

任何“A 比 B 好 / X 月变差”的机制结论，落 FINDINGS.md 前必须引用 `references/hypotheses.md` 里的一条假设 ID（H-ID）。命中已有条目 → 看图后更新它的状态（证实/推翻/证据不足）与证据链接；表里没有能对应的条目 → **先新增一条“预注册”**（写清可判别预测，再去验），不要跳过登记直接下结论——这道门就是防“看到结果再编机制故事”。

## 3. 反驳门（结论升级为“已证实”前的最后一关）

过了稳健性门槛，只证明“差异不是噪声”；还要证明“差异不是别的原因造成的”。把结论写进 FINDINGS.md 并标“已证实”之前，逐条走下面的替代解释清单。每一条**要么给出排除证据**（引用具体图 / stats.json 数值 / references 事实），**要么显式标注“未排除”并把该结论降级为“假设”**（不得标“已证实”）：

1. **事件/限电/停机**：差距发生的时段，是否落在 `<project-context>/event-log.md` 记录的变更、或 `suspect_days.csv` 命中的日期上？未排除 → 差距可能是运维事件、不是模型能力。
2. **样本量不足**：涉及的分组（天气类型/单月/口径拆分）是否 ≥10 天？不足 → 只描趋势，降级为“假设”。
3. **天气占比变化冒充能力变化**：X 月变差是“坏天占比升高”还是“类内能力退化”？用图#8 的占比分解拆开；没拆 → 未排除。
4. **跨站分布外/漂移**：留出站该月是否偏出训练站的分布（图#11/#12 出现高 PSI，run_drift 逐站）？有高漂移却没纳入讨论 → 未排除“没见过这个站的这种天（跨站 OOD）”。
5. **NWP/气象原料变差**：气象原料本身是否同步变差（图#10，或用晴天功率做代理证据）？没查 → 无法区分“原料坏了”与“模型退化”。
6. **Chronos 等共享上游**：涉及 M1/M3/M4 时，变差是否来自共享的 Chronos、而非该模型本体？对照 `hypotheses.md` 的 H-CHRONOS-1 / H-WXSRC-1 三角条目判定。
7. **口径/取点/对齐错误**：本次质检与口径对账是否已通过？取点索引、窗口一致性、行对齐任一存疑 → 结论不可信，先回 Step 1/Step 2 复核。

逐条走完后，在 ANALYSIS.md 里留一小段“反驳门记录”——写清哪几条已排除、凭什么排除，哪几条未排除、导致结论降级；让后续会话看得到这道关是怎么过的。

## 4. 分组样本量披露

任何分组统计（天气类型、单月、口径拆分）给结论前，先报告每组的天数/样本数；组内不足 10 天的，只描述趋势、不下定论、不进 FINDINGS.md（或标注“样本不足”）。突变日这类稀有类别尤其容易只有两三天——在三个点上做 Wilcoxon 检验没有意义。

## 5. 顶层结论台账 FINDINGS.md（技能工作目录根下）

每条结论记一行，含四项：**结论、证据链接**（指向 ANALYSIS.md/图）、**状态**、**日期**。状态只能取这四个值：

- **现象** = Stage 3 产出的未归因观察，只有数字和图证据（不含机制语言）；
- **假设** = 已登记 H-ID、但还没过反驳门；
- **已证实** = 过了稳健性门槛 + 反驳门；
- **被推翻** = 证据否定了它。

每次分析结束都同步更新它；新分析开始前先读它，避免重复劳动、避免前后结论打架。

结论示例句式：

- “M1 与 M2 的 over_error 相关系数 0.93，高度同质化，ensemble 对这两者的组合增益有限。”
- “4 月 x–y 日的低估时段里，M1 的负 bias 明显深于 M2；而在高估时段两者接近——M1 存在不对称的低估倾向。”

## 6. 展示纪律

分析完成后，把关键图与结论**直接展示**给用户（图 + stats.json 里的数字 + 一段结论），不要只丢一堆文件路径。

## 7. 运行后回顾（每次实跑收尾必做）

本技能靠“用得越多越准”改进——但只有把每次实跑暴露的问题**写回技能文件**才算数。每次真正跑过数据后，收尾做三件事：

1. **回顾本次执行轨迹里指令层面的文字反馈**：哪条 SKILL 指令缺失/写错/有歧义、害你走了弯路？哪个 `scripts/` 函数被迫临时改（列名对不上、口径取点错、边界情况没覆盖）？哪个 references/ 约定被数据推翻？这些“反馈”就是本次要吸收的信号。
2. **把修正直接写回技能文件**——不只是改 scripts：
   - 脚本 bug/列名 → 改 `scripts/`（优先改 `data_utils.py` 顶部的 CONFIG）。
   - 指令歧义、缺步骤、口径措辞 → 改 `SKILL.md`。
   - 确认的新项目事实（限电段、气象源切换、模型细节）→ 补对应的 `references/`。
   - 首跑固化下来的 `generate_report` 调用方式 → 填进 SKILL 的“已固化调用”小节。
3. **每次改动都在技能根目录 `CHANGELOG.md` 追加一行**：`日期 | 改了哪个文件的哪节 | 触发这次改动的反馈原文（一句话） | 为什么这么改`。变更可追溯 = 改错了能回滚——别让技能在无记录的连续微调里悄悄退化。
